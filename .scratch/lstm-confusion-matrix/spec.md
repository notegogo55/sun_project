# Spec — แผง Confusion Matrix ของโมเดลพยากรณ์ flare

**สถานะ:** ready-for-agent
**ขอบเขต:** `backend/scripts/train_lstm.py`, `backend/src/sunseg/metrics.py`, `backend/app/routers/forecast.py`, `backend/app/services.py`, `frontend/`
**ที่มา:** บทสัมภาษณ์ออกแบบ (grill) 14 ข้อ · ทุกข้อตัดสินแล้ว ไม่มีข้อค้าง

---

## Problem Statement

หน้าเว็บของ sunseg รายงานผลของโมเดลพยากรณ์ flare เป็นตัวเลขสรุปเพียงแถวเดียวในตาราง
"ผลการทดลอง" (val TSS, test TSS, test AUC, test recall) ซึ่งบอกไม่ได้ว่าโมเดล **ผิดพลาดแบบไหน**

ผู้ที่เข้ามาดูงานนี้ — อาจารย์ที่ปรึกษา, กรรมการสอบ, หรือคนที่จะนำไปใช้ต่อ — ต้องการเห็นสิ่งที่
ตัวเลข TSS เดียวซ่อนไว้:

- โมเดลจับ flare ได้กี่ครั้งจากทั้งหมด และ **แลกมาด้วย false alarm กี่ครั้ง**
- ถ้าขยับเส้นตัดสินใจ (threshold) ให้ระวังมากขึ้นหรือน้อยลง จะได้/เสียอะไร
- flare ที่โมเดล **พลาด** คือดวงไหน เกิดเมื่อไหร่ ไปดูข้อมูลจริงของมันได้ที่ไหน

ข้อมูลที่ต้องใช้ตอบคำถามเหล่านี้มีอยู่ในระบบแล้วทั้งหมด (`artifacts/metrics/lstm.json` เก็บ
tp/fp/tn/fn ไว้ และ `meta.parquet` รู้ว่า sample ไหนอยู่ split ไหน) แต่ไม่มีทางเข้าถึงจากหน้าเว็บ

ปัญหาซ้อน: `train_lstm.py` คำนวณค่าทำนายราย sample (`p_test`) แล้ว **ทิ้งไป** เก็บไว้แต่ตัวเลข
สรุป ทำให้ทำอะไรกับมันต่อไม่ได้เลย และ baseline logistic ไม่ได้เซฟทั้งโมเดลและค่าทำนาย

## Solution

เพิ่ม **บล็อกที่สามในส่วน "เกี่ยวกับงานนี้"** ของหน้าเว็บ ต่อจากตารางผลการทดลองและการแบ่งข้อมูล:
ตาราง confusion matrix ขนาด 2×2 ที่ผู้ใช้เลื่อน threshold ดูได้แบบทันที พร้อมคลิกเข้าไปดูว่า
แต่ละช่องมี active region ดวงไหนอยู่บ้าง

รูปแบบที่ผู้ใช้เห็น:

- **ตาราง 2×2** — แถวคือสิ่งที่โมเดลทำนาย คอลัมน์คือสิ่งที่เกิดขึ้นจริง เรียง positive ก่อน
  ตามธรรมเนียม contingency table ของวงการ space weather แต่ละช่องมีทั้งชื่อทางสถิติ
  (TP/FP/FN/TN) และคำเรียกของวงการ (hit / false alarm / miss / correct negative)
- **สไลเดอร์ threshold** — ขยับแล้วตัวเลขทั้ง 4 ช่องและตัวชี้วัด (TSS, recall, precision, HSS2)
  เปลี่ยนทันที ค่าเริ่มต้นคือ threshold ที่ freeze ไว้จาก validation
- **ตัวสลับโมเดล** — LSTM / logistic baseline สลับแล้วสไลเดอร์รีเซ็ตกลับไปที่ threshold
  จาก val ของโมเดลนั้น
- **ตัวสลับ split** — test (ค่าเริ่มต้น) / val โดย val ติดป้ายชัดว่าเป็นชุดที่ใช้เลือก threshold
  ไม่ใช่ตัวเลขที่รายงาน
- **คลิกช่องใดช่องหนึ่ง** → ลิสต์ sample ในช่องนั้น (HARP, NOAA AR, เวลาออกพยากรณ์,
  ค่าความน่าจะเป็น) → คลิก sample → เลื่อนขึ้นไป dashboard พร้อมเลือก HARP นั้นและ
  ขยับช่วงวันที่ให้ครอบเวลานั้น

## User Stories

1. ในฐานะกรรมการสอบ ฉันอยากเห็น confusion matrix ของโมเดลพยากรณ์ เพื่อจะได้รู้ว่าตัวเลข TSS มาจากการนับแบบไหน
2. ในฐานะกรรมการสอบ ฉันอยากเห็นทั้งจำนวนนับและสัดส่วนของแถวในแต่ละช่อง เพื่อจะได้ตีความได้ทั้งในเชิงจำนวนเหตุการณ์และเชิงอัตรา
3. ในฐานะคนที่คุ้นกับวงการ space weather ฉันอยากเห็นตารางเรียงแบบ forecast × observed พร้อมคำว่า hit / false alarm / miss / correct negative เพื่อจะได้อ่านได้โดยไม่ต้องแปลงหัวในใจ
4. ในฐานะคนที่คุ้นกับ machine learning ฉันอยากเห็นชื่อ TP/FP/FN/TN กำกับอยู่ด้วย เพื่อจะได้เชื่อมกับสิ่งที่ตัวเองรู้อยู่แล้ว
5. ในฐานะผู้ใช้ ฉันอยากเลื่อน threshold แล้วเห็นตัวเลขขยับทันที เพื่อจะได้รู้สึกถึงการแลกกันระหว่าง recall กับ false alarm ด้วยตัวเอง
6. ในฐานะผู้ใช้ ฉันอยากเห็น TSS, recall, precision, HSS2 ขยับไปพร้อมกับตาราง เพื่อจะได้รู้ว่า threshold ที่ตัวเองเลือกดีหรือแย่กว่าค่าที่ระบบใช้อยู่
7. ในฐานะผู้ใช้ ฉันอยากเห็นเครื่องหมายบอกตำแหน่ง threshold ที่ระบบ freeze ไว้บนสไลเดอร์ เพื่อจะได้รู้ว่าตัวเองเลื่อนออกจากค่าที่รายงานไปไกลแค่ไหน
8. ในฐานะผู้ใช้ ฉันอยากกดกลับไปที่ค่า threshold เดิมได้ในคลิกเดียว เพื่อจะได้ไม่ต้องเลื่อนหาเอง
9. ในฐานะผู้ใช้ ฉันอยากสลับดูระหว่าง LSTM กับ logistic baseline เพื่อจะได้เห็นด้วยตาว่าทำไม baseline ถึงชนะ
10. ในฐานะผู้ใช้ ฉันอยากให้สไลเดอร์รีเซ็ตไปที่ threshold ของโมเดลที่เพิ่งสลับมา เพื่อจะได้ไม่เผลอเทียบสองโมเดลที่คนละจุดทำงานโดยไม่รู้ตัว
11. ในฐานะผู้ใช้ ฉันอยากสลับดู split test กับ val เพื่อจะได้เห็นว่าโมเดลดูดีบน val แล้วแย่ลงบน test มากแค่ไหน
12. ในฐานะผู้ใช้ ฉันอยากเห็นป้ายเตือนบน val ว่าเป็นชุดที่ใช้เลือก threshold เพื่อจะได้ไม่หยิบตัวเลขนั้นไปอ้างเป็นผลงาน
13. ในฐานะผู้ใช้ ฉันอยากเห็นจำนวน sample และจำนวน positive ของ split ที่กำลังดูอยู่ เพื่อจะได้รู้ว่าตัวเลขที่เห็นตั้งอยู่บนเหตุการณ์กี่เหตุการณ์
14. ในฐานะนักวิจัย ฉันอยากคลิกช่อง miss แล้วเห็นรายการ flare ที่โมเดลพลาดทั้งหมด เพื่อจะได้ไล่ดูทีละดวงว่ามีอะไรร่วมกัน
15. ในฐานะนักวิจัย ฉันอยากเห็น HARP, NOAA AR, เวลาออกพยากรณ์ และค่าความน่าจะเป็นของแต่ละ sample ในลิสต์ เพื่อจะได้รู้ว่าโมเดลพลาดแบบ "เกือบถึง" หรือ "ไม่เห็นเลย"
16. ในฐานะนักวิจัย ฉันอยากให้ลิสต์เรียงตามค่าความน่าจะเป็น เพื่อจะได้เห็นเคสที่น่าสนใจที่สุดก่อน
17. ในฐานะนักวิจัย ฉันอยากคลิก sample ในลิสต์แล้วกระโดดไปดู AR ดวงนั้นใน dashboard เพื่อจะได้ดูเส้นความเสี่ยงตามเวลาและค่า SHARP ของมันจริง ๆ
18. ในฐานะนักวิจัย ฉันอยากให้ช่วงวันที่ของ dashboard ขยับตามไปด้วยตอนกระโดด เพื่อจะได้ไม่เจอกราฟว่างเพราะช่วงวันที่ยังค้างอยู่ที่ค่าปริยาย
19. ในฐานะผู้ใช้ ฉันอยากให้ลิสต์ที่ยาวมาก (เช่นช่อง correct negative ที่มีเกือบหมื่นแถว) ถูกตัดให้เหลือเท่าที่ดูไหว พร้อมบอกจำนวนเต็ม เพื่อจะได้ไม่ทำให้หน้าเว็บค้าง
20. ในฐานะผู้ใช้ ฉันอยากให้แผงนี้บอกวิธีแก้เมื่อยังไม่มีข้อมูล แทนที่จะพังทั้งหน้า เหมือนแผงอื่นของแอปนี้
21. ในฐานะคนที่เพิ่ง clone โปรเจคมา ฉันอยากให้หน้าเว็บยังเปิดได้ตามปกติแม้ยังไม่ได้เทรนโมเดลใหม่
22. ในฐานะผู้ดูแลโปรเจค ฉันอยากให้ตัวเลขในแผงนี้ตรงกับที่ README และตารางผลการทดลองรายงานไว้เป๊ะ เพื่อจะได้ไม่มีตัวเลขสองชุดขัดกันเองในงานเดียว
23. ในฐานะผู้ดูแลโปรเจค ฉันอยากให้สไลเดอร์ในแผงนี้ไม่ไปเปลี่ยน threshold ที่ระบบใช้พยากรณ์จริง เพื่อจะได้ไม่กระทบส่วนอื่นของ dashboard
24. ในฐานะผู้ดูแลโปรเจค ฉันอยากให้ค่าทำนายราย sample ถูกเก็บไว้เป็นไฟล์ เพื่อจะได้เอาไปวิเคราะห์ต่อโดยไม่ต้องเทรนใหม่
25. ในฐานะนักพัฒนาที่มารับงานต่อ ฉันอยากให้มีหน้าเว็บชุดเดียวใน repo เพื่อจะได้ไม่แก้ผิดไฟล์แล้วงงว่าทำไมไม่มีอะไรเปลี่ยน
26. ในฐานะผู้ใช้บนมือถือ ฉันอยากให้ตารางและลิสต์ยังอ่านได้บนจอแคบ

## Implementation Decisions

### แหล่งข้อมูล — เซฟตอนเทรน ไม่ใช่คำนวณใหม่ตอน request

`train_lstm.py` ต้องเซฟค่าทำนายราย sample ลง artifacts เพิ่มจากที่เซฟ metrics สรุปอยู่แล้ว

เหตุผลที่ไม่คำนวณใหม่ในเว็บ: โมเดลถูกเทรนบน GPU แต่ webapp รันบน CPU ความต่างระดับทศนิยม
ทำให้ sample ที่อยู่ชิด threshold พลิกฝั่งได้ ผลคือ confusion matrix บนหน้าเว็บจะไม่ตรงกับ
tp=19 / fp=405 ที่ตารางข้าง ๆ ในหน้าเดียวกันรายงานอยู่ — ตัวเลขสองชุดขัดกันเองในงานเดียวคือ
ปัญหาที่ร้ายแรงกว่าความไม่สะดวกของการต้องเทรนใหม่ (ซึ่งใช้เวลาไม่กี่นาทีตาม README)

สิ่งที่เซฟ: หนึ่งแถวต่อหนึ่ง sample ของ **split val และ test** (ไม่เอา train — ทำให้ไฟล์โตขึ้น
20 เท่าและชวนให้เข้าใจผิดว่าเป็นผลงาน) แต่ละแถวมี split, HARPNUM, NOAA AR, เวลาออกพยากรณ์,
label จริง, ค่าความน่าจะเป็นจาก LSTM และค่าความน่าจะเป็นจาก baseline logistic

รูปแบบไฟล์: parquet ไฟล์เดียว วางข้าง `lstm.json` ใน `artifacts/metrics/` — โปรเจคใช้ parquet
กับ metadata อยู่แล้ว (`meta.parquet`, `frame_wcs.parquet`) และ `.gitignore` กัน `artifacts/`
กับ `*.parquet` ไว้อยู่แล้ว จึงไม่มีปัญหาเรื่องขนาด repo

`run_baseline()` ต้องคืนค่าความน่าจะเป็นของ val และ test ออกมาด้วย ไม่ใช่คืนแค่ report

### สัญญาของ API

**endpoint สรุป** — รับ split กับ model คืน:

- ตาราง sweep ของ threshold: `np.linspace(0.01, 0.99, 200)` พร้อม tp/fp/tn/fn ของทุกจุด
  (ใช้กริดเดียวกับ `find_best_threshold` เพราะ threshold ที่ freeze ไว้ 0.33994974… มาจากกริดนี้พอดี
  ค่าเริ่มต้นจึงตกลงจุด sweep ตรง ๆ ไม่ต้องปัดเศษ)
- threshold ที่ freeze ไว้ของโมเดลนั้น
- ตัวชี้วัดที่ไม่ขึ้นกับ threshold (AUC) และขนาดของ split (n, n_positive)

payload ราว 5 KB ต่อชุด สไลเดอร์จึงลื่นโดยไม่ยิง network เลยหลังโหลดครั้งแรก

**endpoint ลิสต์ sample** — รับ split, model, threshold และช่องที่คลิก (tp/fp/fn/tn) คืนรายการ
sample ในช่องนั้น เรียงตามค่าความน่าจะเป็นจากมากไปน้อย จำกัดจำนวนที่คืน พร้อมบอกจำนวนเต็ม
ของช่องนั้น เรียกเฉพาะตอนคลิก — ข้อมูลราย sample ของ val (26,255 แถว) จึงไม่ต้องข้ามสายไป
ทั้งก้อน

### การนับอยู่ฝั่ง Python เสมอ

ตรรกะการนับ TP/FP/TN/FN และการคำนวณตัวชี้วัดต้องอยู่ใน `sunseg.metrics` ซึ่งมี `test_metrics.py`
คุมอยู่แล้ว ห้ามย้ายไปนับใน `app.js` — ฝั่ง JS ของโปรเจคนี้ไม่มี test เลยสักตัว การย้ายตรรกะที่
สำคัญที่สุดของฟีเจอร์ไปไว้ในที่ที่ทดสอบไม่ได้คือการแลกที่ไม่คุ้ม

เพิ่มฟังก์ชันกวาด threshold ตัวใหม่ใน `sunseg.metrics` ที่รับ y_true, y_prob และรายการ threshold
แล้วคืนจำนวนนับของทุกจุด ต้องให้ผลตรงกับการเรียก `confusion_counts` ทีละจุด (คุณสมบัติที่
ทดสอบได้ตรง ๆ)

`app.js` มีหน้าที่แค่: ดึง sweep มาเก็บไว้ → เปิดตารางที่ index ตาม threshold ที่สไลเดอร์ชี้ →
คำนวณ TSS/recall/precision จากจำนวนนับ 4 ตัว (เลขคณิตล้วน) → วาด

### สถานะของโมเดลไม่ถูกแตะ

สไลเดอร์เป็นของแผงนี้เท่านั้น ห้ามเขียนทับ `services.forecast.threshold` ซึ่งเป็นค่าที่
`/api/forecast` และ `/api/forecast/at` ใช้ตัดสิน `predicted_positive` และ `risk_level` ให้กับ
ทั้ง dashboard — threshold ที่ผู้ใช้ลากเล่นต้องไม่รั่วออกไปนอกแผง

### ตำแหน่งและรูปแบบบนหน้าเว็บ

วางเป็น `results__block` ก้อนที่สามในส่วน about ไม่ใช่การ์ดใน dashboard เพราะทุกการ์ดใน
dashboard ขยับตามช่วงวันที่ใน filterbar พร้อมกันเสมอ (เป็นสัญญาที่เขียนไว้ในคอมเมนต์หัวไฟล์
`app.js`) แต่แผงนี้ตรึงอยู่กับ split ถาวร ไม่ขยับตามตัวกรอง — วางปนกันจะสื่อความหมายผิด

เรนเดอร์เป็นตาราง HTML/CSS ไม่ใช่ Plotly แม้กราฟอื่นทั้งหมดจะใช้ Plotly ก็ตาม เหตุผล:
TN มีเกือบหมื่นส่วน FN มีสิบกว่า การไล่สี heatmap ตามจำนวนนับจะทำให้สามช่องกลายเป็นสี
เดียวกันหมด สื่ออะไรไม่ได้ ส่วน log scale ก็เข้าใจยากเกินไปสำหรับตาราง 2×2 — ให้ลงสีตาม
**บทบาทของช่อง** แทน (hit / miss / false alarm / correct negative) และอ่านสีจาก CSS custom

### การ degrade เมื่อยังไม่มีข้อมูล

ทำตามธรรมเนียมของแอปนี้: ถ้าไม่มีไฟล์ค่าทำนาย endpoint คืน 503 พร้อมข้อความบอกว่าต้องรัน
สคริปต์ไหน และแผงแสดงข้อความนั้นแทนตาราง หน้าเว็บส่วนอื่นต้องเปิดได้ตามปกติ

### หนี้ที่ต้องเก็บก่อน

`backend/app/static/` มี index.html / app.js / style.css เวอร์ชันเก่าที่ไม่มีโค้ดส่วนไหนอ้างถึงเลย
(`main.py` เสิร์ฟจาก `frontend/` เท่านั้น) แต่ Dockerfile ยัง COPY ติดเข้า image — ต้องลบทิ้งก่อน
เริ่มงานจริง ไม่งั้นคนที่มาทำ ticket มีโอกาสสูงที่จะแก้ผิดไฟล์แล้วงงว่าทำไมหน้าเว็บไม่เปลี่ยน

## Testing Decisions

### test ที่ดีในงานนี้คืออะไร

ทดสอบพฤติกรรมที่มองเห็นจากภายนอก ไม่ใช่รายละเอียดภายใน — ยิง endpoint แล้วดูสิ่งที่คืนมา
ไม่ใช่เรียกเมธอดภายในของ service หรือตรวจว่าเรียกฟังก์ชันไหนกี่ครั้ง test ต้องไม่พังเมื่อเปลี่ยน
วิธีคำนวณภายในโดยที่ผลลัพธ์ยังเท่าเดิม

### รอยต่อที่ใช้ — ของเดิมทั้งคู่ ไม่สร้างใหม่

**รอยต่อที่ 1: HTTP ผ่าน `TestClient(app)`** — ของเดิมใน `test_app_smoke.py` เป็นรอยต่อสูงสุด
ที่โปรเจคมี ใช้ทดสอบ:

- endpoint สรุปคืน sweep ที่มีจุดครบตามกริด และมี threshold ที่ freeze ไว้อยู่ในกริดนั้นจริง
- จำนวนนับ ณ threshold ที่ freeze ไว้ ต้องตรงกับที่ `artifacts/metrics/lstm.json` รายงาน
  (test ที่สำคัญที่สุดของงานนี้ — เป็นตัวกันไม่ให้มีตัวเลขสองชุดขัดกันในหน้าเดียว)
- สลับ model แล้วได้ threshold คนละค่า
- สลับ split แล้วขนาดของชุดเปลี่ยนตาม
- endpoint ลิสต์ sample คืนจำนวนแถวไม่เกินที่จำกัดไว้ เรียงถูก และรายงานจำนวนเต็มของช่อง
- ช่อง miss ณ threshold ที่ freeze ไว้ ต้องมีจำนวนเท่ากับ fn ที่รายงานไว้
- ไม่มีไฟล์ค่าทำนาย → 503 พร้อมข้อความที่บอกวิธีแก้ ไม่ใช่ 500
- `/api/forecast` ยังคืน threshold เดิมหลังเรียก endpoint ใหม่ด้วย threshold อื่น
  (พิสูจน์ว่าสไลเดอร์ไม่รั่ว)

**รอยต่อที่ 2: ฟังก์ชันใน `sunseg.metrics`** — ของเดิมใน `test_metrics.py` ใช้ทดสอบฟังก์ชัน
กวาด threshold ตัวใหม่: ผลต้องตรงกับการเรียก `confusion_counts` ทีละจุด, จำนวนนับรวมกัน
ได้เท่าจำนวน sample เสมอทุกจุด, threshold ต่ำสุดทำนาย positive หมด, สูงสุดทำนาย negative หมด

**ไม่สร้างรอยต่อฝั่ง JS** — ตรวจหน้าเว็บด้วยตา การเพิ่ม Playwright/vitest เป็น dependency,
CI และเวลารันชุดใหม่ทั้งชุดสำหรับแผงเดียวไม่คุ้ม และตรรกะที่ผิดแล้วเจ็บถูกกันไว้ที่รอยต่อที่ 1
กับ 2 หมดแล้ว

### prior art ในโปรเจค

- `backend/tests/test_app_smoke.py` — คลาส `TestSystemEndpoints` และ `TestGracefulDegradation`
  เป็นแบบให้ทั้งการยิง endpoint และการตรวจว่า 503 มีข้อความที่ใช้ได้จริง
- `backend/tests/test_metrics.py` — แบบของการทดสอบฟังก์ชันตัวชี้วัดด้วยเคสที่คำนวณมือได้
- test ต้องข้ามได้อย่างสุภาพเมื่อเครื่องที่รันยังไม่มีโมเดล/ข้อมูล ตามที่ `test_app_smoke.py` ทำอยู่

## Out of Scope

- **กราฟ ROC / PR curve และ reliability diagram** — ข้อมูล sweep ที่ส่งมาพอจะวาด ROC ได้ แต่
  เป็นคนละเรื่องกับ confusion matrix เก็บไว้เป็น issue แยก (README ระบุว่า BSS ติดลบเพราะ
  ความน่าจะเป็นยังไม่ calibrate — reliability diagram ควรมาพร้อมกับการทำ calibration จริง)
- **confusion matrix ของ U-Net** — ยังไม่ได้เทรน และ CM ระดับพิกเซลต้องเล่าเรื่องคนละแบบ
- **ปุ่ม export CSV ของ sample ในช่อง**
- **confusion matrix ตามช่วงวันที่หรือราย HARP ที่ผู้ใช้เลือกเอง** — subset แบบนั้นคร่อม
  train/val/test ปนกัน ตัวเลขที่ได้จะไม่ใช่ผลประเมินที่เชื่อถือได้ และขัดกับกติกากัน data leakage
  4 ข้อที่ README ยืนยันไว้
- **การเปลี่ยน threshold ที่ระบบใช้จริงจากหน้าเว็บ**
- **calibration (isotonic / Platt)** — README เสนอไว้เป็นทางปรับปรุง แต่เป็นงานฝั่งโมเดล
- **split train** — ไม่เก็บและไม่แสดง
- **การตั้งค่า issue tracker จริงให้โปรเจค** — ยังไม่ได้ init git ด้วยซ้ำ ใช้ไฟล์ local ไปก่อน
